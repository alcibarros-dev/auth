O que aconteceu quando você entrou

Foram cinco passos, em menos de um segundo. O mais importante: a sua senha só passou pelo servidor de autorização. Esta aplicação nunca a viu.

  1. Você clicou em Entrar. Esta aplicação mandou o seu navegador para o servidor de autorização, dizendo quem ela é (notas-web) e o que quer (openid email).
  2. Você digitou e-mail e senha na página do servidor de autorização, não nesta. Ele conferiu e abriu uma sessão para você lá (cookie AUTHSESSION).
  3. Ele devolveu o seu navegador para cá com um código, que vale uma vez só e por pouco tempo.
  4. Esta aplicação trocou o código pelos tokens, falando direto com o servidor de autorização, sem passar pelo navegador e mostrando a senha dela (o segredo do cliente).
  5. Pronto. Os tokens ficaram guardados aqui, no servidor desta aplicação, e o seu navegador recebeu só o cookie NOTASWEB. Quando esta página precisa da API, é esta aplicação que leva o access token até ela.
Detalhes técnicos: código de autorização com PKCE

No passo 1, esta aplicação gerou e guardou na sua sessão um state (contra CSRF), um nonce (amarra o id_token a este pedido) e um code_verifier secreto, e mandou para /oauth2/authorize o code_challenge, que é o SHA-256 do verifier. No passo 4, a troca em /oauth2/token leva o código, o verifier e o segredo (Basic). Quem roubasse o código no caminho não conseguiria trocá-lo: faltariam o segredo e o verifier. Esse é o PKCE, que o servidor exige de todos os clientes.

JWT é lacrado, não trancado. Qualquer pessoa que tenha um JWT consegue ler o que está escrito nele: é só texto em Base64. O que ninguém consegue é alterar sem que a API perceba, porque a assinatura (o lacre) deixaria de bater. Por isso um token nunca leva senha nem segredo, e por isso ele precisa ser guardado com cuidado: quem o tiver entra na API como você até ele vencer.

Onde fica cada coisa

O JWT fica guardado no Redis, e o usuário recebe um token opaco?

Quase. O Redis não guarda token nenhum: o servidor de autorização usa o Redis só para contar tentativas (o limite de logins por minuto, por exemplo). Os tokens que ele emite ficam no PostgreSQL. E sim, nesta aplicação, o seu navegador recebe só algo opaco: um cookie de sessão. Os tokens ficam na memória do servidor desta aplicação.

E num app que roda só no navegador ou numa CLI? Aí não há um servidor no meio: o próprio app recebe o access token (o JWT) e o guarda. É o caso do Swagger UI e do demo.sh, na seção Formas de login.

O que a API faz com o token

Esta aplicação acabou de chamar a API com o seu access token. Do outro lado, a API fez quatro coisas, sem perguntar nada ao servidor de autorização:

  1. Conferiu o lacre com a chave pública (que ela baixou uma vez e guarda).
  2. Conferiu se é para ela e se está no prazo: emissor (iss), destino (aud = notas-api) e validade (exp).
  3. Descobriu qual conta é a sua: pegou o sub e procurou a conta local com ele. No seu primeiro acesso, criou essa conta.
  4. Entregou só o número da conta ao código das notas. O código de negócio nunca vê o token: recebe @CurrentUser long contaId e pronto.

Experimente

Cada botão faz uma chamada de verdade ao servidor de autorização. O resultado aparece no topo da página, explicado.

1. Renovar

Troca o refresh token por um access token novo, sem senha.

Observe: o jti e o exp do access token mudam.

2. Perguntar ao servidor

"Este token ainda vale?" (introspecção). É o único jeito de saber algo sobre o refresh token.

3. Revogar

Cancela a autorização no servidor.

Observe: o servidor diz que o token não vale mais, mas a API continua aceitando até ele vencer. Depois, tente Renovar.

4. Sair de tudo

Encerra a sessão aqui e a do servidor de autorização.

Observe: o próximo Entrar pede a senha de novo.

Permissões e papéis

O token de hoje diz quem você é, mas não diz o que você pode fazer dentro da aplicação. Não há papéis (como "admin" ou "leitor") nele.

O que existe é o scope, que é outra coisa: o que você deixou esta aplicação fazer em seu nome. Aqui, openid (fazer o seu login) e email (ver o seu e-mail). O Spring transformou isso nestas permissões nesta aplicação:

SCOPE_email

Como ter papéis com o que existe hoje

Recomendado

Papel na conta da API

A API já sabe qual é a sua conta (pelo sub). Basta a conta ter uma coluna papel no banco da API, e o código decidir com ela. Não muda nada no auth, e trocar o papel de alguém vale na hora.

Para limitar aplicações

Escopo por cliente

Cada aplicação registrada no servidor declara os escopos que pode pedir. Serve para limitar o que uma aplicação faz (uma CLI só de leitura, por exemplo), não um usuário.

Não existe hoje

Papel dentro do token

Exigiria o servidor de autorização escrever um claim novo, o que ele não faz. E um papel no token só muda quando o token é renovado.

Hoje a API deixa entrar qualquer pessoa logada com um token válido para ela. Quem pode o quê lá dentro é decisão da própria API.

O que o auth faz, e o que não faz

O auth são duas coisas: o servidor de autorização, que roda como uma imagem Docker igual para todos os projetos, e as bibliotecas que a API de cada projeto usa para conferir os tokens.

Servidor (imagem)

Páginas de login, cadastro e troca de senha; emite os tokens. Cada projeto o configura com um arquivo: quais aplicações podem entrar, para qual API são os tokens, o nome nas páginas.

auth-security

Vai na API. Confere o token a cada pedido e responde 401 ou 403 quando não pode. Esta aplicação web não o usa: ela pede tokens, não recebe.

auth-security-api e auth-support

O que o código de negócio da API usa: @CurrentUser para saber quem é o usuário, e um formato único para as mensagens de erro.

Faz hojeNão faz hoje
  • Login, logout e cadastro, com sessão própria (entrar uma vez vale para todos os apps do projeto)
  • Troca de senha, que desconecta os outros acessos
  • Login de sites (com e sem servidor) e de terminal
  • Renovar o acesso sem senha (para sites com servidor)
  • Perguntar se um token vale, e cancelar um token
  • Trocar a chave de assinatura sem derrubar ninguém
  • Limitar tentativas de login e cadastro
  • Papéis ou grupos dentro do token
  • Login de máquina para máquina (client credentials)
  • Login com senha digitada direto no app (proibido no OAuth 2.1)
  • Login social, segundo fator (MFA)
  • Verificar o e-mail, apagar a conta

Glossário

OAuth 2.1
As regras de como uma aplicação ganha permissão para agir em nome de alguém sem saber a senha dessa pessoa.
OpenID Connect (OIDC)
Uma camada sobre o OAuth para o login: acrescenta o id_token e o /userinfo.
Servidor de autorização
Quem confere a senha e emite os tokens. Aqui, o auth.
Cliente
A aplicação que pede tokens: este site, o Swagger UI, a CLI. Cada um é registrado no servidor com um client_id.
Servidor de recurso
Quem recebe e confere os tokens: a API.
JWT
Um formato de token: um texto em três partes (cabeçalho, conteúdo, assinatura) que qualquer um lê e ninguém altera sem ser notado.
Claim
Cada informação dentro de um JWT, como sub ou exp.
Assinatura e JWKS
O lacre do JWT, feito com a chave privada do servidor. O JWKS é a lista das chaves públicas, com que qualquer um confere o lacre.
Escopo (scope)
O que o usuário autorizou a aplicação a fazer em nome dele.
PKCE
Uma proteção do login: o código que volta pelo navegador só pode ser trocado por quem começou o login.
BFF (backend for frontend)
Um servidor que guarda os tokens pelo navegador, como esta aplicação. O navegador fica só com um cookie.
Introspecção
Perguntar ao servidor de autorização se um token ainda vale.
Revogação
Pedir ao servidor de autorização que cancele um token.
